If you have only created Employee #1, then:

GET /api/employees/1

finds the employee → 200 OK ✅

But:

GET /api/employees/2

can't find an employee with ID 2.

Why are you getting 500?

Your Service currently has:

public Employee getEmployeeById(Long id) {
    return employeeRepository.findById(id)
            .orElseThrow();
}

If ID 2 doesn't exist:

findById(2)
     ↓
Optional.empty()
     ↓
.orElseThrow()
     ↓
Exception
     ↓
500 Internal Server Error

So your application is behaving exactly according to the code we wrote, but 500 isn't the ideal response for a missing employee.

In a professional REST API, we'd normally want:

GET /api/employees/2
        ↓
Employee doesn't exist
        ↓
404 Not Found

# EXCEPTION HANDLING AND GLOBAL EXCEPTION HANDLING

So, for all the globalexception, I can do the same methods rite :@ExceptionHandler(EmployeeNotFoundException.class)     @ResponseStatus(HttpStatus.NOT_FOUND)     public String handleEmployeeNotFound(EmployeeNotFoundException ex) {         return ex.getMessage();     }

Yes — the pattern is the same, but the exception type, HTTP status, method name, and response can change depending on the problem.

For example, if later you create a DepartmentNotFoundException, you could have:

@ExceptionHandler(DepartmentNotFoundException.class)
@ResponseStatus(HttpStatus.NOT_FOUND)
public String handleDepartmentNotFound(DepartmentNotFoundException ex) {
    return ex.getMessage();
}

And for a bad request:

@ExceptionHandler(IllegalArgumentException.class)
@ResponseStatus(HttpStatus.BAD_REQUEST)
public String handleBadRequest(IllegalArgumentException ex) {
    return ex.getMessage();
}
The pattern to remember
@ExceptionHandler(WHAT_EXCEPTION)
@ResponseStatus(WHAT_HTTP_STATUS)
public String handleSomething(EXCEPTION_OBJECT ex) {
    return ex.getMessage();
}

So you can think of it as a template:

Part	Purpose
@ExceptionHandler(...)	Which exception should I catch?
@ResponseStatus(...)	What HTTP status should I return?
handleSomething(...)	What should I call the handling method?
ex	The actual exception object
ex.getMessage()	Get the error message

One important point: you don't need a separate handler for every single exception. Later, we'll learn how to handle groups of exceptions and return a more professional JSON error response

INPUT DATA ROLES:
Usually, the developer defines the JSON structure, but the client/user provides the actual data.

Think of it like a form.

In a real workplace

The backend developer defines what the API expects:

{
  "firstName": "string",
  "lastName": "string",
  "email": "string",
  "phone": "string",
  "salary": 50000
}

The developer says, essentially:

"If you want to create an employee, send me these fields in this format."

Then the frontend application—usually built by another developer or frontend team—creates the actual request:

{
  "firstName": "John",
  "lastName": "Smith",
  "email": "john@example.com",
  "phone": "555-1234",
  "salary": 60000
}

The end user normally doesn't manually type JSON.

Instead:

Employee enters information in a web form
              ↓
Frontend collects the information
              ↓
Frontend creates JSON request
              ↓
Backend API receives JSON
              ↓
EmployeeRequest DTO
              ↓
Employee entity
              ↓
Database
What you're doing with Postman

You're basically pretending to be the frontend.

When you manually enter:

{
  "firstName": "John",
  "lastName": "Smith"
}

you're simulating the request that a real frontend would send.

So as a Java backend developer, you generally don't spend your workday manually creating JSON. You build the API contract and
backend logic, while the frontend/client sends the data according to that contract.

That's one reason your EmployeeHub project is useful: Postman is letting you play both sides while you're learning.

Request DTO vs Response DTO

Right now you have:

EmployeeRequest

Its job is:

Data coming INTO the backend.

For example:

{
  "firstName": "John",
  "lastName": "Smith",
  "email": "john@example.com",
  "phone": "555-1234",
  "salary": 60000
}

But when the backend sends data BACK to the frontend, we may not want to send exactly the same information.

For example, your database Employee entity might eventually contain:

id
firstName
lastName
email
phone
salary
department
createdAt
updatedAt

You might want the API response to contain only:

{
  "id": 3,
  "firstName": "John",
  "lastName": "Smith",
  "email": "john@example.com"
}

That's where a response DTO comes in.

Think of it like this
              BACKEND

Client ──→ EmployeeRequest ──→ Employee ──→ Database

Client ←── EmployeeResponse ←── Employee

Request DTO = what we're willing to receive.

Response DTO = what we're willing to send back.

This separation becomes especially important in larger applications because you don't want to accidentally expose internal/database information.

For EmployeeHub

We're going to eventually have:

dto/
├── EmployeeRequest.java
└── EmployeeResponse.java

But don't create EmployeeResponse yet.

For now, just remember this distinction. Your next coding step will be creating the response DTO.

You've covered the important practical concepts:

What a DTO is — separates API data from the entity.
Request DTO — data coming into the backend.
Response DTO — data going back to the client.
DTO validation with @Valid.
DTO → Entity mapping.
Entity → Response DTO mapping.
Why repositories expect the Entity, not the DTO.
Why DTOs help prevent exposing database/internal fields.
Why different operations can use different DTOs.
Understanding that DTOs can look identical to entities in JSON even though they're different Java classes.

Swagger/OpenAPI::
  It is primarily API documentation. It describes your endpoints and tells developers how to use them.

For EmployeeHub, it can document:

GET    /api/employees
POST   /api/employees
PUT    /api/employees/{id}
DELETE /api/employees/{id}

Along with:

What each endpoint does
Required parameters
Request JSON structure
Response structure
Expected HTTP status codes
Validation/errors
Authentication requirements

And Swagger UI also lets you try the endpoints directly, which is why it has some testing capability.

So your mental model is right:

Swagger = documentation of your API + an interactive way to try it.

You don't need to memorize a bunch of Swagger code. For your job prep, understand what it is, why teams use it, and
how to navigate/use Swagger UI.
